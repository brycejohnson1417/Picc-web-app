## 1. Problem

PICC field reps (Bryce first, then Ben, Eric, and the rest of the team) need store intelligence in the field without calling Laura or digging through Notion, Sheets, Nabis, and Distru. The data already exists across five sources. What is missing is one guarded tool layer that any AI agent (Muse first, also Claude, ChatGPT, Town) can call with a small set of fixed commands, returning the same simple format every time.

The rep-facing product is already designed in the PICC Rep Copilot app (Muse artifact, shared separately). This PRD covers only the backend: an MCP server on piccnewyork.org plus the data aggregation behind it.

## 2. Product principles (from Travis, non-negotiable)

1. Simple, stupid baseline. Three code phrases cover 90 percent of rep use: Store Report, Attack List, Route Me. Depth (order history graphs, RFM, trajectory) is returned only when explicitly requested.
2. Fixed output format. The same report shape every time, generated by deterministic rules, not free-form LLM text. The agent words the result; it never invents a number.
3. Every number carries its source and as-of timestamp.
4. Action plan is rules-based, in this priority order: (a) payment required first, with named open invoices; (b) push SKUs and brands the store does not carry; (c) if no order in about 2 months, get an order and find out why they stopped; (d) if not PPP, get them on PPP; (e) if a good payer, pitch the 25 percent one-day-a-week sale day.
5. Reports list only what a store does NOT carry. If it carries everything, say so in one line. Never list both.
6. Difficult accounts are flagged in the data (Do Not Target / low rank) and are ranked last or excluded from attack lists. Bad data (for example a travel agency in the dispensary list) must never waste a top-10 slot.

## 3. Tools to expose (MCP, Streamable HTTP)

Endpoint: POST /api/mcp on piccnewyork.org, served from this repo, following the MCP spec current at build time. All tools are read-only in v1 except create_checkin (Phase 2, behind a flag).

### 3.1 store_report
Input: { store_query: string } (name or partial name; resolve against account records, return a disambiguation list when more than one match)
Output (JSON, stable schema):
- store: name, address, neighborhood, primary contact name
- credit_status (for example Send/Good), nabis_rating, days_overdue (max across open invoices), payment_average_days, orders_paid
- payment_required: boolean; open_invoices: [{ invoice_number, amount, days_overdue, source_note }] when payment_required is true
- ppp: { enrolled: boolean, type: string or null } (for example Self-Managed)
- headset_connected: boolean
- last_order: { date, amount }, last_sample: { date }
- last_vmi_check: { date, status } or null (from Laura's VMI tracker data once ingested; null in v1 is acceptable, field must exist)
- carries_count and catalog_count (for example 6 of 10)
- missing_skus: [names] only
- displays: { present: [names], missing: [names] }
- action_plan: [{ priority, action, detail }] generated by the rules in section 2.4, server-side
- sources: [{ field_group, source_system, as_of }]

### 3.2 attack_list
Input: { area: string (neighborhood, borough, or region), limit: number default 10, offset: number default 0, filters?: { sampled_within_days?: number, sampled_sort?: "earliest_first" | "latest_first", sampled_not_closed?: boolean, not_carrying_pcc?: boolean, include_difficult?: boolean default false } }
Ranking (server-side, deterministic, documented in code):
1. Previously ordered and now dormant (months since last order, longer ranks higher)
2. Credit good / fast payer ranks up; COD and slow pay rank down
3. Sampled recently ranks up
4. Recent engagement or conversation ranks up
5. Do Not Target or difficult flag ranks last and is excluded unless include_difficult is true
Output: ranked stores with name, address, neighborhood, orders count, last order amount and date, months quiet, credit status, rank_reason (one plain line per store explaining why it ranked there).

### 3.3 route_top10
Input: { origin: string (address or lat/lng), area?: string, limit: number default 10 }
Behavior: take the attack_list ranking for the area, order the top N into an efficient route starting at origin using the app's existing route and Google Maps infrastructure (Google Maps is the only supported map provider in this repo). Output: ordered stops with store, address, leg, and a per-stop directions URL. Do not introduce a new mapping provider.

### 3.4 order_history (deep dive, only on explicit request)
Input: { store_query: string, months?: number default 12 }
Output: monthly order totals and counts suitable for charting, plus RFM segment (champion, loyal, dormant, etc.) when available from the RFM data already in the workspace.

### 3.5 create_checkin (Phase 2, feature-flagged off in v1)
Input: { store_query, note, sample_requests?: [product names], follow_up_date?: date }
Behavior: write a comment-first check-in (repo rule: check-ins are comment-first) and return the created record id. Must be behind MCP_ENABLE_WRITES=false by default.

## 4. Data sources and boundaries

Keep every external system behind an explicit module in lib/server, per ARCHITECTURE.md. No tool may call an external API inline.

1. App Postgres (Prisma): accounts, territory, contacts, routes, check-ins. This is the app's own system of record for field activity.
2. Notion-derived account data: Dispensary Master List CRM fields (account status, PPP, contacts, follow-up dates) as already ingested by this app. Do not build a second Notion ingestion path; reuse the existing boundary.
3. Sales NY / SYNC (Notion SYNC database, synced from the Sales NY workbook): credit status, Nabis rating, days overdue, payment average, orders paid, last order date and amount, last sample date, product carry dates, and all display dates (SMACK Display, CHAMPS Display, Sushi Hash Display, Chopsticks Display, Oh Yeah Display, LED Screen, Neon Sign). This is the source for the financial and display fields in store_report.
4. Nabis (existing cached retailer and order module in this repo): credit rating, payment behavior, order history. Reuse the existing cache; do not add a second Nabis integration.
5. Distru (NEW boundary, lib/server/distru): PICC sells through Distru (Emcann menu) since the November 2026 distribution switch. Distru data is required for: live inventory and product catalog (the carries / missing calculation must reflect the current catalog), Distru sales orders and invoices (open invoice detail for payment-required stores), and Distru Commerce marketplace orders (a PPP store ordering on the marketplace must be visible so the rep can notify Laura; alerting itself is Phase 2, the data read is v1).
   - Preferred access: Distru's official MCP server at https://mcp.distru.com/mcp (Streamable HTTP). Server-side client only. Auth: API key created in Distru under Settings, Distru MCP (requires the Manage MCP API Keys permission), stored as a Vercel env var DISTRU_MCP_API_KEY and sent as a Bearer token. Never expose the key to the client or to the rep-facing MCP tools' outputs.
   - Fallback: Distru REST API https://app.distru.com/public/v1/ with a Bearer API token (env var DISTRU_API_TOKEN) if MCP access is not enabled on the PICC Distru account.
   - Prerequisite outside this repo: Distru MCP access must be enabled for the PICC account by a Distru representative. If it is not enabled, build against the REST fallback and leave the MCP client behind the same boundary interface.
   - Cache Distru reads (orders, invoices, inventory) with a short TTL (15 minutes) and record as_of on every response.
6. Headset: sell-through connection status per store (boolean in v1, from existing account data where present).

Field ownership when sources disagree (v1 rule, Travis to confirm): SYNC wins for credit, payment, and order facts; CRM wins for contacts, PPP, and account status; Distru wins for live inventory and open marketplace orders; app Postgres wins for check-ins and routes. Log conflicts at debug level, never block a report on a conflict.

## 5. Auth and access control

- The MCP endpoint must not be public. Require a per-agent bearer token (env-configured, rotatable) at minimum in v1, and keep the existing Clerk session model for any browser surface. Access stays restricted to PICC staff.
- This is an auth and access-control change: under this repo's AGENTS.md it is APPROVAL LANE. Build it, open the PR, and post the approval request comment in the required format instead of merging. Do not deploy the MCP endpoint to production until Bryce replies approved on the PR.
- No production data writes, no schema migration in v1. If the Do Not Target flag has no existing field, add it as a nullable Prisma field ONLY inside the same approval-lane PR and call it out explicitly in the PR body; otherwise store the flag in existing account metadata.
